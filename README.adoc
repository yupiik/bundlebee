Yupiik Bundlebee is a powerful, lightweight tool designed to simplify Kubernetes deployments and resource management by packaging Kubernetes manifests into easily reusable and maintainable bundles.

== 🚀 Key Features

- **Reusable Bundles**: Package Kubernetes resources into reusable bundles for simplified management.
- **Declarative Configuration**: Define application deployments and Kubernetes resources clearly and simply.
- **Variable Substitution & Templating**: Easily customize bundles dynamically based on deployment environments.
- **Flexible Deployment**: Deploy Kubernetes manifests selectively or entirely in one simple command.
- **Integrates with Kubernetes**: Seamlessly integrates with standard Kubernetes tools and workflows.
- **CLI & Automation Friendly**: Simple yet powerful command-line interface for automation and scripting.

In Bundlebee, a bundle is called an `alveoli`.

== 📦 Installation

Quickly install Bundlebee using the provided installer:

[source,bash]
----
curl -L https://yupiik.github.io/bundlebee/install/install.sh
bundlebee version
----

Or use it directly from your Maven project:

[source,xml]
----
<dependency>
    <groupId>io.yupiik</groupId>
    <artifactId>bundlebee-core</artifactId>
    <version>2.0.0-SNAPSHOT</version>
</dependency>
----

== 🛠️ Useful Commands

- Deploy resources:
[source,bash]
----
bundlebee apply --alveolus=my-bundle
----

- List available bundles:
[source,bash]
----
bundlebee list
----

- Inspect resource details:
[source,bash]
----
bundlebee inspect --alveolus=my-bundle
----

- Remove resources:
[source,bash]
----
bundlebee delete --alveolus=my-bundle
----

=== Build

Pre-requisite: Apache Maven >= 3.8 running on JDK 21 or 25.
We kept the Java 17 baseline, but the build requires Java 21 for formatting tooling.
Application compilation and Javadoc remain targeted at Java 17; running BundleBee still requires only Java 17 or newer.
The current development version is `2.0.0-SNAPSHOT` and uses Yupiik Fusion `1.2.1-SNAPSHOT` for dependency injection, configuration and JSON.
Until Fusion `1.2.1` is available from Maven Central, builds require the locally installed Fusion fixes described in the migration guide.
See link:bundlebee-documentation/src/main/minisite/content/migration-2.adoc[the migration guide] and link:bundlebee-documentation/src/main/minisite/content/extensions.adoc[the Java extension guide] before upgrading a CDI-based extension.

=== Formatting

Spotless checks formatting during `compile`, inherited by application modules and explicitly configured in the standalone `packaging-verification` project, which has no root parent.
It covers handwritten `src/main/java`, `src/test/java` and `src/main/java-templates` files, shortens fully qualified types, removes unused imports, sorts each module's POM, and applies whitespace/newline hygiene to `.gitignore` and `.gitattributes` where present.
The current Java templates contain Maven placeholders only inside string literals (`${project.version}`), so they are included without filtering those values; generated Java/output directories are excluded.
Artifact-specific incremental indexes live under `.mvn/.spotless/` and are ignored by Git, including for standalone builds.

The configuration follows `yupiik-ai`, using one Palantir version consistently in the reactor and standalone verifier, without adopting its Java 25 application baseline.

[cols="1,1,3",options="header"]
|===
|Component |Selection |Requirement
|Spotless Maven plugin |3.12.0 |Runs during `compile`; the selected formatter raises the build JDK requirement to 21+.
|Palantir Java Format |2.103.0 |Requires JDK 21; verified on build JDKs 21 and 25.
|===

With Maven running on JDK 21 or 25, run `mvn spotless:apply` at the repository root and `mvn -f packaging-verification/pom.xml spotless:apply` for the standalone verifier, review the changes, then use the corresponding `spotless:check` goals.
JDK 27 is not supported by the selected formatter: its javac internals changed, causing `NoSuchFieldError` during formatting.
CI distinguishes the build JDK from the test runtime: the Java 17 runtime lane builds and formats on JDK 21 and forks Surefire on Java 17 using the standard `-Djvm=/path/to/jdk17/bin/java` option.
The Java 21 and 25 lanes build and test on their respective JDKs; native packaging runs only in the Java 21 lane.
